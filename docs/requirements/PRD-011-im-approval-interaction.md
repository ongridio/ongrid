# PRD-011：IM 审批交互闭环

状态：实现中，真实平台验收待完成。日期：2026-11-01。
设计：[HLD-003](../design/HLD-003-im-approval-interaction.md)。

## 问题与目标

用户从 Slack、Telegram、钉钉、飞书向 Agent 发起操作后，需要知道哪些操作在等待确认、去哪里确认、是否执行成功。当前已有富文本、分页和审批通知代码，但通知没有直达入口，审批者身份尚未绑定，消息状态更新依赖当前运行。不能把四个平台的代码测试等同于真实机器人验收。

目标是四个平台具有相同的业务语义：知情确认、按实际权限决策、明确展示结果；排版与编辑能力允许按平台降级。

## 范围与优先级

| 阶段 | 用户能力 | 验收条件 |
|---|---|---|
| P1 | IM 收到安全摘要，打开 Ongrid 登录后审批，结果回到原线程 | 四个平台分别完成批准、拒绝、失效与通知重试；当前有效 Agent 能继续 |
| P2 | 绑定平台账号后，直接点击批准或拒绝 | 实时权限检查、重复回调与越权测试通过；审批审计记录真实审批人 |
| 后续 | 重启后的持久化续跑、进度和取消、文件交互 | 单独设计，不计入本期完成条件 |

P1 不要求用户绑定 IM 身份；使用已登录 Ongrid 账号的审批权限。飞书 P2 以卡片内闭环为准，不依赖 Web 跳转；其他平台暂保留原有 Web 兼容入口。

## 产品要求

1. 飞书原生卡片展示审批编号、脱敏后的完整操作参数、批准/拒绝和执行结果。操作参数必须使用纯文本，递归隐藏执行令牌和常见凭证。不可完整展示时只提供拒绝，不允许盲批。其他平台兼容通知仍只显示安全摘要。
2. 飞书批准和拒绝均使用卡片内二次确认；无跳转链接，回调只提交随机动作令牌。其他平台打开链接仍不会批准操作。
3. 已批准、已执行、失败和失效必须区分；执行结果未知时不显示成功。
4. 同一审批只能产生一次有效决策；重复点击返回当前结果。
5. 通知失败不改变审批结果，能够重试和补发；不得因此再次执行操作。
6. Agent 已停止、请求已失效或执行上下文丢失时，明确要求重新发起，不自动重新批准。
7. 群聊成员身份不等于 Ongrid 管理员，机器人服务账号不代表点击者。

## 验收与不包含项

验收记录须区分单元测试、模拟平台契约测试和真实机器人 E2E。四个平台均需覆盖正常消息、长消息、批准、拒绝、通知失败恢复与无权限访问，并清理测试数据。

本期不重写审批状态机、不改变 v2/v3 运行时归属、不承诺外部副作用恰好执行一次，也不将 IM 通知持久化视作 Agent 持久化恢复。

## 无网页身份授权

管理员可通过受认证 API 预先授权本人的精确平台身份（应用、租户 scope、用户 Open ID）。机器人私聊 `/whoami` 返回平台认证的不可变身份供核对，不自动授权、不进入模型、不按昵称或最近发言人匹配。已有 Web 双向绑定保留，但不是 IM 审批前置条件。

首次管理员的授权必须由现有可信管理渠道完成；本期不新增“陌生用户申请、管理员卡片授予账号权限”的第二套审批体系。

### 2026-11-01：用户自助绑定闭环

复用「设置 → IM → 我的 IM 审批身份」入口和既有四张表，不新增重复身份体系。
用户生成一次性绑定码，在所选机器人私聊 `/bind`（Slack 为 `/ongrid-bind`），页面自动检测认领后，由当前登录账号显式确认。绑定码十分钟过期且只能认领一次。页面提供复制命令、失效提示、绑定完成反馈和解绑反馈。

卡片未绑定提示直接说明该入口；不要求用户执行 `/whoami` 或把平台 ID 交给维护人员。保留实时审批权限校验，不因为绑定而授予管理员权限，不因绑定完成而自动批准已有操作。未绑定、无权限、卡片失效、审批状态变化、暂时服务异常分别提示。

多人分别绑定自己的 Ongrid 账号；既有数据模型允许一账号绑定多个身份，同应用同平台身份仍保持唯一。无需数据库 migration。回滚本次前后端版本即可恢复原手动检查流程，既有绑定仍兼容。
