# ADR-036：IM 审批复用平台审批权威与执行链路

状态：提议。日期：2026-11-01。
关联：[PRD-011](../requirements/PRD-011-im-approval-interaction.md)、[HLD-003](../design/HLD-003-im-approval-interaction.md)。

## 背景

现有 approvals 表已经保存决策和执行结果，执行器按 Kind 与 RuntimeVersion 路由。IM 使用共享服务账号发起会话，尚不能证明消息发送者具有平台审批权限。Agent 的部分待执行回调存于内存，进程重启后不可恢复。

## 决策

1. approvals 继续作为唯一审批事实来源；IM 只保存通知投递记录，不另建审批执行状态机。
2. 先实现登录 Web 审批的完整闭环，再在双向身份绑定、共同授权入口和平台回调验证完成后开放原生按钮。
3. HTTP 和原生 IM 决策复用同一鉴权服务入口。真实审批人必须有当时有效的权限，禁止用机器人服务账号代替。
4. 通知按至少一次投递设计；并发决策依赖现有数据库条件更新。外部执行结果不确定时不自动重试。
5. 当前等待者继续通过现有 broker 获取结果。进程重启后的执行恢复另行设计，不在通知功能中偷偷实现。

## 备选方案与后果

直接把批准按钮接到现有业务方法，虽然改动少，但会绕过 HTTP 层管理员检查，不能采用。为 IM 新建审批表会造成两套状态与审计，不能采用。等待完整持久化 runtime 后才支持审批入口，会延迟可独立交付的用户能力，也不采用。

代价是 P1 需要跳转浏览器，P2 需要新增身份绑定与回调适配。收益是授权边界清晰、平台行为一致，现有 Web 审批与运行时归属不被破坏。
