模型为现有配置的 `openai / gpt-6.1-terra`，推理级别 Low。通过正常聊天页面发送 [cases.json](../../scripts/result-analysis/cases.json)，没有指定分析工具、提供表达式或透露预期答案。问题要求结构化答案以便精确核对。数据来自只读 `analysis_demo` MCP：每份快照 25,000 条合成项目，包含超 2^53 整数 ID、缺失字段、重复键、排名并列及带引号/换行的 CSV。

这是真实模型和真实聊天调用链上的合成业务场景测试，不是真实生产数据验收。使用独立 SQLite 查询核对最终回答，检查全部命中行、完整整数和 Top 5 顺序。验收脚本还故意修改一个 ID，确认校验器会拒绝错误答案。

## 失败尝试与修正

1. 初次真实调用失败：子进程清空环境后，已有 tokenizer 依赖初始化缓存尝试写 `/.cache`。改为 Runner 私有临时目录，结束后清理，未恢复业务环境变量继承。
2. 首轮去重表达式反复更新高基数对象，触发内存分配上限。模型自行改成只收集必要字段后成功。
3. 首轮关联反复构建大对象并尝试并行重试。六次分析调用中只有三次进入执行，其余被并发容量限制拒绝；随后失败信息使上下文预算耗尽，未形成有效答案。页面将该错误误显示为“每日预算用完”；这不是日配额耗尽。下述后续修复已区分两类提示。
4. 工具说明增加了高基数去重/关联的字段裁剪、`group_by` 和避免并行重复失败计划的指引；内存失败压缩为短提示。重跑去重和关联均一次分析成功。最后补齐不同平台内存错误措辞的归一化，并通过回归测试；未重复整组模型问答。

历史失败会话和原始导出保留，不计入“首次通过”。Manager 在子进程内存失败后继续服务，没有因此重启。

## 流式内存测量

使用实际 Linux worker 做全量计数与求和，并核对结果和完整覆盖。生成器位于父进程，表内只统计 worker；每毫秒采样 exec 后的 `/proc/<pid>/status`，短暂峰值可能遗漏。每项一次运行，不能作为性能保证。

| 格式 | 记录数 | 输入字节 | worker 采样峰值 | 用时 |
| --- | ---: | ---: | ---: | ---: |
| 原生 JSON | 25,000 | 4,750,001 | 57.8 MiB | 0.205 s |
| 原生 JSON | 250,000 | 47,500,001 | 61.8 MiB | 1.636 s |
| MCP 文本内 JSON | 25,000 | 4,950,028 | 60.2 MiB | 0.321 s |
| MCP 文本内 JSON | 250,000 | 49,500,028 | 61.4 MiB | 1.919 s |

这些计数表达式没有保存完整数组，输入扩大十倍时内存基本稳定。另一个显式保留 25,000 条数组的对照为 80.0 MiB。排序、去重、关联仍会保存中间状态，不能据此承诺任意表达式恒定内存。25 万条测试直接进入 worker，超过既有 MCP 的 16 MiB 响应上限，不代表 MCP 已支持该规模的响应。
