# RCA 合成场景的事实与验收规则

本文件对应 `tests/rcaeval/cases/` 的 8 个场景，记录 2026-11-04 场景审查后的事实、可接受结论和限制。

这些场景用于检查诊断是否尊重观测、对象、时间和不确定性。场景数据与期望结论已经逐项核对，但它们仍是合成数据。模型诊断是否正确需要单独复核。

## 每个场景能证明什么

所有时间均为 UTC。默认告警窗口为 2026-11-04 06:00–06:20，现场快照固定在 06:20。指标为明确提供的采样点，不能把稀疏采样解释成连续观测。

| 场景 | 固定事实 | 允许的结论 | 不允许的扩展 |
|---|---|---|---|
| `cpu_process` | 设备 42 的 CPU 在 06:10、06:20 分别为 94%、96%；06:20 的 1 秒进程采样显示 pigz PID 812 占整机容量 91%，压缩一个具体的 tar 文件 | pigz 是采样时的主要 CPU 消耗来源 | 不能证明它在整个 20 分钟内持续占用；不能推断任务启动原因、恶意行为或恢复 |
| `memory_oom` | 同设备内存采样从 80% 到 98%；06:19 的内核日志记录 OOM kill，受害进程为 checkout-api PID 901 | 同窗口发生过 OOM kill | 被杀进程不一定是增长源；不能据此确认泄漏、全局 OOM 与 cgroup OOM 的类型，或服务已恢复 |
| `memory_unproven` | 内存采样从 80% 到 95%；指定时段的 OOM 日志查询成功，结果为空 | 内存上涨，当前查询没有匹配记录 | 不能断言 OOM 绝对不存在、日志覆盖完整、服务正常或发生泄漏 |
| `disk_log_growth` | `/var` 容量 100 GiB，已用从 75 GiB 到 100 GiB；app.log 实际占用从 68 GiB 到 93 GiB；目录占用、文件信息和磁盘指标一致；末端日志记录空间不足 | 日志文件是主要占用来源，25 GiB 增长与文件系统增量一致 | 未证明写入进程、轮转故障、文件系统损坏；未执行删除或恢复 |
| `downstream_dependency` | 一个采样 Trace 中，checkout-api 父 span 失败，inventory-api 子 span 持续 2080 ms 并返回连接池等待超时；同 Trace、同时间日志记录 active=max=20、waiters=80；末端错误率为 35% | 可定位这个采样请求的下游故障环节 | 不能用一个 Trace 解释全部错误请求；不能证明数据库宕机、连接泄漏或慢查询根因 |
| `query_timeout` | 内存采样从 80% 到 95%；日志查询返回超时；关联查询也保留日志失败状态 | 日志证据未获得，OOM 状态未知 | 超时不等于成功空结果；不能确认或排除 OOM |
| `mixed_devices` | 设备 42、43 在 06:20 的 CPU 分别为 95%、94%；42 的 pigz 进程采样成功；43 返回 `dispatch: edge offline` | 42 的当前主要消耗来源可定位，43 的进程原因未知 | 不能跨设备复用 PID、进程或利用率；采集连接不可用不等于主机宕机 |
| `stale_logs` | 当前内存采样上涨，当前窗口的 OOM 查询成功但为空；单独查询前一天窗口才能取得 PID 755 的 OOM 日志 | 旧记录不能证明当前窗口发生 OOM | 当天关联结果不得夹带前一天日志；不能用空查询排除未采集到的事件 |

CPU、内存和磁盘使用与现有工具相容的 PromQL 表达式。表达式运算结果不伪造 `__name__`；设备、挂载点等保留维度与查询一致。服务案例显式声明应用提供 `http_error_ratio` recording rule（5 分钟失败请求数 / 总请求数，按服务和设备分组），不假定 Ongrid 自动提供该指标。

## 工具与场景的一致性

- `get_incident_detail` 的字段来自真实工具实现，包括 `rule`、状态、时间、说明等；不再把关联摘要的 `rule_key` 当成详情字段。
- CPU/内存告警携带真实关联查询支持的 `metric` 标签。磁盘 `/var` 与自定义服务错误率不强行伪装成该工具支持的闭集指标；它们通过直接指标查询取得数据。
- 关联查询、日志查询和独立指标查询使用同一组观测。关联窗口外的旧日志会被过滤；日志失败在各入口保持一致。
- 磁盘日志的文本时间与记录时间一致；文件逻辑大小、实际占用、目录总量和文件系统容量分别核对。
- 专家回放使用实际角色权限：主调查读取 Trace，再将已观察到的内容交给 SRE 专家核对日志。SRE 不被假定拥有 Trace 查询工具。
- 固定回复的结论和每条证据分别引用对应来源；失败设备、空查询、历史日志也有各自引用。专家证据必须来自真实子会话。

`correlate_incident` 及文件、Trace 工具的某些结果目前在证据检查器中属于 `unsupported/context_only`。回放保留这一限制，不把它改写成已验证的因果关系。

## 修改后的验收顺序

从仓库根目录执行：

```sh
make test-rca-eval

go run ./tests/rcaeval -mode smoke -repeat 3 \
  -out /tmp/rca-corpus-review-new
```

第一步检查：

1. 所有已声明参数通过真实工具的 JSON Schema 校验。
2. 详情、关联、PromQL、LogQL、Trace 和变更查询通过真实工具执行器生成响应，与案例逐项比较；后端为固定观测，无外部网络调用。
3. 主机工具通过现有 wire DTO 检查完整格式，另查设备顺序、批量成功数、采样口径及数值。
4. 指标标签、时间范围、日志筛选、Trace 父子关系、磁盘容量和固定结论的引用满足场景约束。
5. 故意修改设备、服务、挂载点、日志日期、事件时间或成功数量时，检查必须失败；固定回复调用未开放工具时也必须失败。

第二步使用真实调查运行时和存储重复跑通所有场景，保存会话、引用和检查结果。固定回复只是管线验收，不参与模型正确率统计。

然后才运行真实模型。人工按上表和案例 `rubric` 核对报告，不按关键词或固定调用顺序判分。`required_observations` 是复核时的资料提示；允许能够支持同一事实的等价观测和查询路径，不能仅凭某个 fixture ID 未命中判定诊断失败。

## 固定场景后再做优化

- 先固定案例文件、代码版本、提示词、模型参数和预算。每批结果的 manifest 保存文件摘要，每个运行保存实际 case.json。
- 后续只改变提示词、模型或调查策略中的一个因素，并使用同一案例版本比较。
- 如果新增查询变体，必须先证明它返回的设备、时间和筛选结果正确，再重新验收并建立新的基线。不要为了提高通过率扩大匹配范围或直接返回已有答案。
- 未覆盖查询继续标记 `fixture_gap`；它说明评测数据不足，不能直接认定模型诊断错误。
- 2026-11-04 的定向真实模型试跑后，为 `query_timeout`、`mixed_devices`、`memory_oom` 补充了 60 分钟关联查询，以及原表达式的 1 小时、2 小时、24 小时查询；OOM 另补充 40 分钟关联查询。响应通过真实工具与固定后端核对，沿用原有观测，不增加故障事实或期望结论；扩大查询窗口后仍只有已声明的采样点，不能推断整个窗口都有连续数据。其他未提供的进程、主机和原始指标观测仍是覆盖缺口。
- `memory_oom` 与 `query_timeout` 的未声明日志参数使用真实日志工具和本地后端，按设备、明确的 RFC3339 时间、标签和行筛选读取既有日志。仅支持 `=` / `=~` 标签以及至多一个 `|=` / `|~` 行筛选，不支持的语法仍是覆盖缺口。小写 `oom` 和 `error` 不匹配现有 OOM 行时返回空结果；超时场景保留失败，不能因改变窗口或条数变成成功。
- 2026-11-04 首轮 24 次真实模型记录使用的是审查前的案例，包含已确认的数据和引用缺陷。保留用于排查，不作为本版案例的质量基线，不跨版本宣称优化收益。

定向复测使用真实模型与合成观测，未验证真实 Prometheus/Loki/Tempo、Edge 或现场硬件。固定后端只用于验证所声明场景；它不是通用 PromQL/LogQL 引擎，也不覆盖全部合法查询。主机 wire 检查不能替代端到端采集测试。

## 2026-11-04 提示词对照

固定 CPU、混合设备、OOM、日志超时四个案例，每个案例重复三次，对比旧版与新的调查提示词。两组使用相同观测、工具回放、DeepSeek Flash、temperature 0.1 和预算（16 次模型调用、24 次工具调用、300 秒）。每次累计 token 达 100,000 后停止后续调用；这不是计费硬上限。评分条件未发送给模型。

下表由 Codex 助手逐份阅读正文、结构化结论、建议和已取得观测后记录，不是独立人工验收。数字表示每组 12 份报告中出现该类问题的份数；一份可计入多类，不按严重程度加权。明确标为可能的假设本身不记错，但建议中的无依据判读仍记错。

| 报告问题 | 旧版 | 提示词更新 |
|---|---:|---:|
| 对象或因果过度推断 | 12 | 8 |
| 时间或连续性过度推断 | 12 | 3 |
| 误读失败或空结果 | 8 | 0 |
| 建议依据、分类或技术错误 | 11 | 1 |
| 报告内表述冲突 | 7 | 3 |

两组分别有 11/12、10/12 次取得案例的核心观测；取得时均保留对应的直接事实。提示词组有一次 CPU 进程快照和一次 OOM 日志未取得，不能因其回答“未知”就算定位能力通过。全部 24 次都有其他查询覆盖缺口，整次运行仍不可计入诊断通过率；上述数字只描述已取得证据下的表述问题。

本批支持继续采用更明确的证据边界，但小样本和查询路径差异不能证明统计显著性或生产准确率。仍有从单次进程快照推断历史增长、从磁盘容量使用率排除磁盘压力等残留。逐次请求、输出、源码与案例指纹保存在本地评测产物中，不随仓库提交；合并前后的判断均应保留这些限制。
