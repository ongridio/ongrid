# HLD-003：IM 审批交互与可靠通知

状态：方案已确认，代码已实现，真实平台验收待完成。日期：2026-11-01。
关联：[PRD-011](../requirements/PRD-011-im-approval-interaction.md)、[ADR-036](../adr/ADR-036-im-approval-authority.md)。

本方案先完成“IM 通知 → 登录 Ongrid 审批 → 执行 → 状态回写与当前 Agent 继续”，再加入身份绑定和原生批准/拒绝按钮。沿用现有 approvals 表及执行链路，不为 IM 再建一套审批状态机。

本文依据 `/private/tmp/ongrid-snmp-config` 的源码快照核对；该目录当前没有 Git 元数据，不能据此声明变更已经提交或合并。下文“已有”表示代码可见，“拟新增”表示本设计范围；真实四平台机器人验收仍待完成。

## 1. 当前能力和缺口

| 能力 | 当前代码 | 本次目标 |
|---|---|---|
| 富文本 | 四平台适配，超长答案降级为可读文本分页 | 保持；增加审批消息契约测试 |
| 分页重试 | 当前进程内记录成功页，避免重发 | 不把内存去重宣称为跨重启保证 |
| 审批提醒 | approval_pending 发送编号和工具名 | 增加登录后可访问的详情入口 |
| 状态回写 | 工具结束、最终回复时查询并更新 | 独立持久化投递和状态协调，不依赖 stream 存活 |
| 审批权限 | Web 管理员鉴权；IM 适配器仅可读状态 | 原生决策开放前提取共用鉴权入口 |
| IM 身份 | 共享服务账号；平台 sender 尚未绑定账号 | P2 才提供双向身份绑定 |
| Agent 恢复 | 活跃运行等待审批结果；执行回调在内存 | P1 保持现状，明确重启不可续跑的边界 |

现有线程按应用、聊天和平台线程映射至 Ongrid 会话，同群同线程的不同发送者可能共享会话。线程隔离不能替代审批人授权。

## 2. 整体架构

```text
Slack / Telegram / 钉钉 / 飞书
             |
             v
       IM 接入与线程映射 ---------> 当前 Agent runtime（v2 或 v3）
                                          |
                                          | 提出受保护操作
                                          v
                                approvals：唯一审批事实
                                   |              ^
                       安全通知投影 |              | 条件决策 / 执行结果
                                   v              |
                         IM 通知记录与投递器       |
                                   |              |
                         原线程：查看并确认链接    |
                                   |              |
                                   v              |
                         登录后的审批详情页        |
                                   |              |
                         真实用户权限检查 ----------+
                                                  |
                                     Kind + RuntimeVersion 执行器
                                                  |
                           +----------------------+
                           v                      v
                    现有 broker 获得结果      状态协调器读取结果
                           |                      |
                    当前 Agent 继续          更新原 IM 审批消息
                           |
                    正常 IM 答案发送器

P2：平台原生按钮 -> 校验回调 -> 绑定身份 -> 同一鉴权决策入口
```

审批状态、通知投递状态、Agent 运行状态分别由各自已有职责管理，不能互相推导为成功。通知器不执行工具，不发起新的 Agent 轮次，也不代替 broker 恢复运行。

## 3. P1 用户交互

拟新增前端 `/approvals/{id}` 详情路由，复用现有审批查询、批准和拒绝 API。当前后端路由已存在，不假定该独立前端页面已经存在。

```text
需要确认的操作
操作类型：重启服务
审批编号：……
状态：等待确认

[查看详情并确认]  -> Ongrid 登录 -> 审批详情 -> [批准] [拒绝]
```

操作类型使用服务端白名单映射和转义，不能直接转发未经审查的工具参数、Summary 或模型文本。详情页展示授权用户可见的目标、动作、影响及当前有效性；凭证仍需脱敏。原线程只收到最小必要摘要，不自动公开完整执行结果。

链接基于管理员配置的 canonical external base URL 构建，不使用请求 Host 推导域名；生产使用 HTTPS。URL 只定位资源，不含凭证或批准令牌。GET、链接预览、登录回跳均不触发决策。登录 return URL 只接受本站路径。

没有配置外部地址时展示“请在 Ongrid 查看审批编号”，管理设置提示补齐配置；不构造错误链接。不具备消息编辑能力时，追加一条带相同编号的状态通知。

详情页复用现有 UI 组件、布局与中英文切换，验证 light/dark。用户双击、两个管理员同时决策时，页面读取并展示实际胜出的决策。审批详情访问不顺带授予对共享服务账号其他会话的访问权。

## 4. 状态与有效性

保留已有数据库枚举，不通过 IM 新增 running、expired 等审批状态。

| approvals 状态 | IM 文案 | 语义 |
|---|---|---|
| pending | 等待确认 | 尚未决策，还需检查原执行上下文是否有效 |
| approved | 已批准，等待执行结果 | 不等同于工具已经开始或完成 |
| rejected | 已拒绝 | 不执行；Agent 按现有拒绝语义继续 |
| executed | 已执行 | 依据已有成功结果，不由消息发送成功推断 |
| failed | 执行失败 / 请求已失效 | 依据结构化失败原因区分；原因不明时不猜测 |

当前通知将 approved 显示为“执行中”，实现时需要修正。现有模型没有 expires_at，不能用消息发送时间伪造审批截止时间；如展示截止时间，应来自实际审批等待器，由服务层提供可选字段。

等待者取消或超时继续调用已有 InvalidatePending，仅允许失效 pending。原请求已失效后，旧卡片点击只能看到失效结果，不能重建执行回调或自动生成新审批。

批准与失效并发时，以数据库条件更新结果为准。如果批准先胜出，不再把记录改成“未批准的失效”；执行器按自己的上下文处理并记录结果。不能用取消等待者来承诺已经批准的外部操作必然停止。

## 5. 可靠通知：新增投递投影

拟新增 `im_approval_notifications`，仅记录“向哪里通知、已展示到什么状态”，不复制 PayloadJSON，不保存另一份业务决策。

| 字段组 | 设计 |
|---|---|
| 关联 | approval_id、im_app_id、im_threads 的内部主键 |
| 唯一约束 | 同一应用、同一内部线程、同一审批一条记录 |
| 目标 | 关联经过校验的原聊天/线程，必要时保存不可变目标快照，禁止会话重映射后改投其他群 |
| 投递 | 平台 message IDs、已展示状态及内容摘要、投递状态 |
| 重试 | attempt、next_retry_at、租约 owner/expiry、脱敏错误码 |
| 时间 | created_at、updated_at；终态投递完成时间 |

先持久化投递意图，再发送外部消息。多实例 worker 通过带 owner 的租约领取；重试采用退避和抖动，尊重平台限流。编辑失败按错误分类处理：暂时失败重试，明确不可编辑时补发，账号禁用或目标失效则暂停并告警，不能无休止刷屏。

事件只负责降低延迟。周期协调器经消费方接口读取审批事实，更新投递目标状态，并补齐遗漏通知意图。补齐必须核对 SessionID、提出者和原线程归属；只覆盖功能启用后的审批及显式限定的存量 pending，不能启动后重放所有历史审批。

发送成功到 message ID 落库之间存在崩溃窗口。无法使用平台幂等能力时可能产生重复通知，明确按至少一次投递验收；重复消息共享审批编号，不产生第二次业务执行。平台内存分页去重继续保留，但不承担此持久化职责。

协调器每次读取最新事实，终态后不再主动发送旧 pending 内容。外部请求结果不确定时先协调，必要时重写最新状态。消息系统不提供条件编辑时不能承诺瞬间严格有序，验收要求最终收敛且不持续倒退。

暂定保留终态投递记录 30 天，可配置；活跃记录不清理。只清理投影，不删除审批审计。禁止保存凭证明文，错误和日志不得包含原始工具参数。

## 6. 执行与重启边界

当前通用工具审批通过内存 execution token 找到执行闭包，批准后执行器消费该闭包。活跃 Agent 通过已有 broker 等待数据库结果，所以 P1 不需要新增“从 IM 再启动一轮 Agent”的恢复 API。

进程重启会丢失闭包。通知 worker 恢复不代表工具可恢复：

- pending 且确认原执行上下文已丢失：由 runtime 生命周期服务调用已有失效用例；通知器只读取结果。多实例下不能仅凭本进程没有 token 就判断失效，需要确认原 owner 的生命周期。
- approved 但没有确定结果：展示“已批准，执行结果待核实”，不盲目重试，也不伪造 failed 或 executed。进入人工核查/执行器对账。
- 已有终态：只恢复状态投递，不再次执行、不重复恢复 Agent。

批准接口当前会同步调用执行器，客户端断线可能影响执行上下文；网络超时不能被解释为未执行。P1 通过重新查询确认状态，禁止自动重提业务动作。P2 回调必须先快速确认接收，再交给受控后台决策任务，不能把长操作绑定到平台回调请求生命周期。

完整重启续跑需要持久化执行描述、owner 租约、checkpoint、工具幂等和副作用对账，另立 runtime 设计。这不是本次 IM 接入的隐含承诺。

## 7. P2 身份绑定和原生按钮

平台 sender ID 不是 Ongrid user ID。绑定键使用 provider、可信的平台组织范围（如有）、应用和不可变 sender ID；不能使用昵称或未验证 email。Slack 配置的 app_id 可能只是本地标签，不能当作已验证 workspace 身份。

绑定采用双向证明：已登录用户发起一次性短期 challenge，平台经过验证的发送者完成另一端确认。challenge 有 TTL、单次消费，存储摘要；支持解绑和管理员撤销。正式使用时仍检查账号有效性和当前审批权限。

原生回调处理顺序：

```text
平台来源校验 / 防重放
        -> 校验 action 与应用、消息、审批的绑定
        -> 解析已绑定的真实用户
        -> 当前权限与审批范围检查
        -> 原子决策
        -> 既有执行器
        -> 持久化结果与统一通知
```

回调不携带可信命令、RuntimeVersion 或执行结果，以上全部从审批记录读取。动作令牌应短期有效并绑定审批、应用、消息和动作；重复平台回调要返回可理解的当前结果。验签失败不得先创建业务任务。

共用鉴权必须从现有 HTTP 管理员检查中提取到可复用服务入口，再供 HTTP 和 IM adapter 调用。禁止 IM 直接用机器人 serviceUserID 调用 Approve，从而绕过管理员判断。审计记录真实用户，并关联平台主体与来源消息。

现有 approval 模型未含 tenant_id，本设计不宣称已具备共享数据库多租户隔离。P1 沿用当前部署级管理员权限及应用/会话归属校验；若接入租户模式，必须先补齐审批、身份绑定和投递查询的租户范围再开放跨租户部署。

## 8. 平台适配契约

| 平台 | P1 统一承诺 | P2 开放条件 |
|---|---|---|
| Slack | 安全摘要、Web 链接、状态回写或补发 | 验证其实际接入模式的交互回调、身份范围和权限 |
| Telegram | 同上 | 验证 callback 身份、重复投递、消息归属 |
| 钉钉 | 同上；不可编辑时追加状态 | 验证当前机器人模式支持的交互卡片及回调 |
| 飞书 | 同上 | 验证交互卡片回调、来源校验及身份范围 |

业务层只提供安全通知模型，provider adapter 负责渲染与能力降级。`edit_message`、`link_action`、`native_decision` 应是明确能力，不靠 provider 名称假定支持。每个平台完成官方接口核对和真实验收后才打开原生按钮；没有完成时继续显示 Web 链接。

## 9. 模块与 API 改动

| 位置 | 拟改动 |
|---|---|
| imbridge 业务层 | 安全审批通知模型、消费方接口、统一渲染契约；不跨业务包直接调用 |
| service/imbridge | 注入只读审批查询和通知持久化接口；P2 接入共用授权服务 |
| approval 业务层 | 保留条件决策、版本化执行器和终态写入；补齐有效性/失败原因的明确契约 |
| IM repo/model | 投递投影与迁移，P2 再增加身份绑定及回调任务去重存储 |
| bootstrap | 配置外部地址，装配 worker、租约、开关和生命周期 |
| Web | 新审批详情入口，登录回跳，真实状态展示，重复提交处理 |

复用 `/api/v1/approvals/{id}` 和现有 approve/reject 操作。新增响应字段或端点先更新 proto，保持既有调用兼容；实现前核对实际响应包装，不在本功能中顺带破坏现有 API。新增 Handler 补齐 Swagger 注释。

所有跨模块能力通过消费方窄接口和 service 装配，IO 接口接收 context。同步回调的请求 context 与后台任务生命周期分离，后台任务仍有明确超时和关闭策略。

## 10. 验收矩阵

| 场景 | 必须观察到的结果 |
|---|---|
| 四平台批准与拒绝 | 真实账号决策、正确审计、原线程状态更新，活跃 Agent 按结果继续 |
| 重复点击、并发批准/拒绝 | 数据库仅一个有效决策，执行器不因重复请求再次进入 |
| 请求超时、用户停止、失效卡片 | 不恢复失效回调，不自动重新提案 |
| approved 后执行错误 | 显示真实失败，不能因为按钮点击成功显示执行成功 |
| Manager 重启 | 通知可恢复；丢失闭包不宣称续跑；不确定执行结果不自动重试 |
| 平台限流、发送超时、编辑失败 | 有界重试/降级，业务结果不受影响，最终状态收敛 |
| 禁用机器人、线程重映射 | 暂停投递或保留原目标，不转发给新的群/会话 |
| 未登录、无权限、撤销绑定、伪造回调 | 不泄露详情、不产生决策；审计可追踪 |
| 默认 runtime 从 v2 改成 v3 | 已创建审批仍使用其原有 RuntimeVersion |
| 共享群聊和敏感参数 | 群成员不自动获得权限，消息及日志不泄露原始参数 |

单元与并发测试启用 `-race`；平台模拟测试覆盖渲染、分页和回调边界；真实机器人 E2E 独立记录证据并清理会话/审批/投递数据。纯接口 mock 不能替代真实平台验收。UI 必须截图检查 light/dark。

健康条件下，暂定状态变化后 10 秒内启动更新投递，实际端到端延迟另测。监测投递积压、最老待发送年龄、重试/失败数、状态延迟；指标标签只用 provider、结果和错误分类，不放用户、会话或审批 ID。结构化日志用 trace_id 与审批 ID 关联但不记录敏感 payload。上线时为持续积压告警配套暂停、重试、核查 Runbook。

## 11. 实施顺序与回滚

1. **P1a：可用入口。** 确认安全展示字段、修正 approved 文案、配置外部地址、新增详情页及链接。保留现有通知模式作为回退。
2. **P1b：可靠回写。** 新增投递投影、协调与租约 worker，补齐丢失执行上下文的有效性处理和故障测试。P1a 单独上线不代表可靠闭环已完成。
3. **P1c：四平台验收。** 逐个平台验证真实收发、批准、拒绝、失效、重启和限流降级，记录未支持能力。
4. **P2：原生决策。** 先共用鉴权和身份绑定，再逐个平台接按钮、回调去重与后台任务；每个平台独立开关。

数据库采用增量迁移，旧版本允许忽略新投影表。发布先小范围启用通知 worker，确认积压和延迟，再扩展应用范围；避免新旧发送路径同时投递同一审批。关闭开关时停止领取新任务、完成或释放在途租约，恢复旧通知路径，不修改既有审批决策，不删除新增审计数据。

以上为设计阶段的实施顺序；当前实现进展和验收边界见第 13、14 节。完整 runtime 重启续跑和文件传输仍不属于本次范围。

## 13. 2026-11-01 实施进展
